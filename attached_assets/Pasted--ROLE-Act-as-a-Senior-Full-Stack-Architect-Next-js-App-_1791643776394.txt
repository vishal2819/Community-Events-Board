# 1. ASSESSMENT OBJECTIVE

Build a small, polished, responsive application where an administrator manages local events and visitors discover upcoming events, create accounts, select favourite categories, access a personalized feed, save reminders, and personalize event cards.

The assessment explicitly prioritizes quality over a rushed feature list. Keep the solution focused on the stated requirements.

Expected implementation time is approximately four to five hours. Make sensible decisions independently, avoid unnecessary clarification, and prioritize a complete, explainable implementation over architectural complexity.

# 2. MANDATORY TECHNOLOGY STACK

Use the following stack:

- Next.js App Router with a currently supported, compatible stable release.
- TypeScript with strict mode enabled.
- PostgreSQL as the database.
- Prisma ORM for schema management, queries, and migrations.
- Tailwind CSS and shadcn/ui for the interface.
- Zod for request and form validation.

Use compatible, stable package versions. Check the existing lockfile and repository before changing dependencies. Do not introduce NestJS, a separate Express server, MongoDB, Redis, microservices, or paid services.

# 4. DATABASE DESIGN

Use PostgreSQL and Prisma.

Create a normalized relational schema with the following logical entities.

## User

- `id`: UUID or another appropriate stable identifier.
- `email`: unique, normalized email address.
- `passwordHash`: password hash only, never plaintext.
- `createdAt`, `updatedAt`.

## Event

- `id`: UUID or another appropriate stable identifier.
- `title`.
- `category`: enum with `MUSIC`, `WORKSHOP`, `FOOD`, `SPORTS`, `KIDS`.
- `city`.
- `startsAt`: PostgreSQL timestamp with timezone semantics.
- `price`: a suitable decimal or integer representation that avoids floating-point currency errors.
- `description`.
- `imageUrl`: optional or nullable.
- `isActive`: boolean.
- `createdAt`, `updatedAt`.

Store event times consistently in UTC and format them in the visitor's intended display timezone. Use `Asia/Kolkata` as the default display timezone unless the product behavior or existing project configuration specifies otherwise.

## FavouriteCategory

A relational join table connecting users to favourite event categories.

- `userId`.
- `category`.
- Composite primary key or unique constraint on `(userId, category)`.

## EventReminder

A join table connecting users and events.

- `userId`.
- `eventId`.
- `createdAt`.
- Unique constraint on `(userId, eventId)`.

Use this to make reminder operations idempotent and persistent.

## EventCardDesign

Persist the design for a particular user and event.

- `userId`.
- `eventId`.
- `theme`: a validated theme identifier.
- `stickers`: an array of validated sticker identifiers or an equivalent normalized representation.
- `createdAt`, `updatedAt`.
- Unique constraint on `(userId, eventId)`.

If using a PostgreSQL array, enforce the three-sticker maximum and allowed identifiers in server-side application validation. Do not trust client-side constraints.

Use foreign keys and appropriate delete/update behavior. Do not create unrelated tables or unnecessary fields.

Use database enums or equivalent constraints where appropriate.

# 5. ADMIN AUTHENTICATION AND AUTHORIZATION

The assessment allows one hard-coded admin. Implement the simplest secure version.

Use environment variables for:

- `ADMIN_EMAIL`
- `ADMIN_PASSWORD_HASH`
- `JWT_SECRET`
- `DATABASE_URL`

Never hard-code the admin password or JWT secret into committed source code.

Generate and document a secure password-hash setup procedure. Seed or provision the admin safely; do not expose admin credentials in API responses, source code, browser bundles, logs, or Git history.

A local development-only convenience is acceptable only if it is clearly isolated, safe by default, and documented.

Admin authorization must be enforced inside every protected server Route Handler and server-side operation. Hiding admin links, checking a role only in a React component, or redirecting in middleware alone is insufficient.

Use explicit server-side authorization such as `requireAdmin()` and `requireUser()`.

Protect every admin operation, including listing events for administration, creating events, updating event details, and changing event status.

Return appropriate HTTP status codes, such as 401 for unauthenticated requests, 403 for authenticated non-admin users, 400 or 422 for invalid input, and 404 for unavailable resources.

Never allow a visitor to become an administrator by changing request JSON, URL parameters, cookies, or client-side state.

If middleware or proxy-based routing is used, treat it only as an additional navigation guard—not the authorization boundary.

# 6. VISITOR AUTHENTICATION AND JWT

Implement email/password signup and login.

Requirements:

- Normalize and validate email addresses.
- Hash passwords using bcrypt/bcryptjs with an appropriate work factor.
- Enforce a reasonable minimum password length and a documented maximum.
- Never store, return, or log plaintext passwords.
- Use generic authentication errors that do not unnecessarily reveal account existence.
- Sign JWTs using a strong secret from the environment, with an explicit algorithm, expiration, and relevant claims.
- Verify signature, algorithm, expiration, and expected claims on the server.
- Never trust a decoded but unverified JWT.
- Do not store access tokens in `localStorage` or `sessionStorage`.

The login JSON API must return a JWT token to satisfy the assessment's explicit requirement. Also establish an appropriate browser session using an `HttpOnly`, `Secure` in production, `SameSite` cookie.

Keep the browser's authentication flow and the mobile/API token flow compatible with the same authentication service. Do not return the JWT secret, password hash, or unnecessary internal fields.

For browser requests that rely on cookies, account for CSRF risk using an appropriate SameSite policy and Origin/CSRF validation for state-changing requests. Do not assume that `HttpOnly` alone prevents CSRF or XSS.

If both bearer tokens and cookies are accepted, define an explicit precedence and verification policy. Never let an untrusted alternate credential override a valid security decision.

Add lightweight rate limiting or an equivalent documented mitigation for login and signup if it can be implemented reliably within the project. Do not add a complex infrastructure dependency solely for this purpose.

# 7. API CONTRACT

Implement versionable, predictable JSON endpoints using Next.js Route Handlers.

Use consistent success/error response shapes, correct HTTP status codes, request validation, and explicit response DTOs.

Implement at least the following endpoints. The exact HTTP method and path can be adjusted to a consistent REST convention.

## Authentication

- `POST /api/auth/signup`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`

Signup creates a visitor account. Login returns a JWT and establishes the browser session. Logout clears the browser session appropriately. `/me` returns only safe user information.

## Public Events

- `GET /api/events`
- `GET /api/events/[id]`

The listing endpoint supports category, city, text search, page, and page size.

Only active, upcoming events are returned from the public listing.

The event-detail endpoint must not accidentally disclose inactive or unauthorized administrative records.

## Admin Events

- `GET /api/admin/events`
- `POST /api/admin/events`
- `PATCH /api/admin/events/[id]`

Admin event listing may include past and inactive events. Creating and updating an event require admin authorization.

Use `PATCH` to update the active/inactive state and other permitted event fields. Never implement event deletion.

## Favourite Categories and Feed

- `GET /api/favourites`
- `PUT /api/favourites`
- `GET /api/feed`

Persist favourite categories for the authenticated visitor.

The feed contains only upcoming, active events whose categories match the user's saved favourites. Return a friendly empty result when no matches exist.

## Reminders

- `GET /api/reminders`
- `PUT /api/events/[id]/reminder`
- `DELETE /api/events/[id]/reminder`

Require authentication. Make the create/remove operations idempotent. Do not allow reminders for nonexistent or ineligible events. If the user removes a reminder, the operation must persist across refreshes.

## Event Card Design

- `GET /api/events/[id]/card-design`
- `PUT /api/events/[id]/card-design`

Require authentication. Persist the selected theme and stickers for that user/event pair.

Validate the theme against exactly three allowed theme identifiers, validate stickers against exactly five allowed sticker identifiers, reject more than three stickers, and reject duplicate stickers unless duplicates are deliberately supported and documented.

Return the saved design so the client can reconcile its state.

Never accept `userId` from the request body as the authority for ownership. Derive the current user from the verified session.

Document all implemented endpoints and response examples in the README or an API reference document.

# 8. EVENT FILTERING, SORTING AND PAGINATION

Implement filtering in PostgreSQL through Prisma queries—not by fetching every event and filtering in JavaScript.

The public events endpoint must combine all supplied filters using AND semantics.

For example:

`category=MUSIC&city=Coimbatore&search=night&page=1&pageSize=9`

must return only active, upcoming events that match the category, city, and search term.

Requirements:

- Filter by category.
- Filter by city.
- Search relevant event text, including title and optionally description/city.
- Normalize city input consistently.
- Use case-insensitive text matching where supported.
- Sort by event start time ascending, nearest upcoming event first.
- Exclude past events using a consistent server-side timestamp.
- Apply pagination after filters.
- Return pagination metadata, including current page and total matching results.
- Enforce a reasonable maximum page size.
- Validate and normalize all query parameters.

Do not interpolate untrusted input into raw SQL.

Add an appropriate composite B-tree index for the common active/upcoming listing and sorting query, considering fields such as `isActive` and `startsAt`. Evaluate a category-plus-date index based on the actual Prisma query plan and access pattern.

Document that ordinary B-tree indexes do not efficiently solve arbitrary substring search. If using PostgreSQL `ILIKE '%term%'`, consider `pg_trgm` with GIN/GiST indexes only if supported and practical in the chosen migration setup. Do not claim that a B-tree index accelerates leading-wildcard substring searches.

Keep the implementation proportional to the assessment.

# 9. ADMIN EVENT VALIDATION

Validate event input on the server using Zod, even if the browser validates the same fields.

Required fields:

- Title.
- Category.
- City.
- Date and time.
- Price.
- Description.

Image URL may be optional, but if provided it must be a valid, acceptable HTTP/HTTPS URL.

Enforce reasonable field-length limits, nonnegative prices, valid dates, and allowed categories.

Reject malformed JSON and invalid enum values. Handle missing events and conflicting updates gracefully.

Render prices in Indian currency format, for example `₹1,50,000`, using `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR', maximumFractionDigits: 2 })` or an appropriate equivalent.

Render event dates in a friendly format, for example `Sat, 18 Oct, 6:30 PM`, using a consistent timezone and locale policy.

Never treat the client-provided date, price, category, or active status as trusted.

# 10. REMINDER OPTIMISTIC UI

The reminder button must update immediately on interaction.

Implementation requirements:

1. Read the initial reminder state from the API or server-provided data.
2. Apply the optimistic state update.
3. Send the request to the application's JSON API.
4. Reconcile state with the successful server response.
5. If the request fails, restore the previous state and show a clear error message.
6. Prevent conflicting repeated operations while an individual request is pending.
7. Ensure a refresh restores the persisted state.

The UI must not silently imply that an unsuccessful reminder was saved.

Treat this as a real application with a small attack surface.

- Password hashing; never plaintext passwords.
- Secure JWT configuration and verification.
- HttpOnly session cookies for browser authentication.

Avoid unnecessary security complexity that cannot be maintained or explained.
